# v0.3.0: teams, operations, hardening and speed

> Steps use checkbox (`- [ ]`) syntax for tracking. Follow the rules in AGENTS.md.

**Goal:** v0.3.0 makes transponder ready for a team to run in production. It adds roadmap items 7 and 8 from the README (sign-in with OIDC, roles and access per route, the admin API with OpenAPI and an audit log, Postgres and several replicas, metrics, tracing and a five-minute demo), and it makes what v0.2.4 already does correct under stress, measurably faster, and easy to adopt. Every claim in the release notes is backed by a test or a measured number.

**Spec:** [docs/design.md](../design.md) sections 8 (identity and roles), 10 (usage and budgets), 11 (admin API), 12 (store) and 13 (operations), and the shared conventions in [CONTRACT.md](https://github.com/raven-clown/mothership/blob/main/CONTRACT.md) (identity, headers, admin API shape, roles, metrics names, scale rules).

**How the work is split:** ten workstreams run in parallel, each in its own session and branch off `next/v0.3.0`. Each workstream opens pull requests into `next/v0.3.0`, not into `main`. When every workstream is done, one pull request takes `next/v0.3.0` into `main`, and v0.3.0 is released from it.

| Workstream | Branch | Owns |
|---|---|---|
| A. Benchmarks and bottlenecks | `v030/bench` | `bench/`, `*_bench_test.go`, `docs/benchmarks.md`, hot-path changes the profiles point at |
| B. Bugs on the request path | `v030/request-path` | `internal/server`, `internal/dialect`, `internal/sse`, `internal/provider`, `internal/tokens` |
| C. Bugs on the control path and failure modes | `v030/control-path` | `internal/config`, `internal/router`, `internal/limits`, `internal/store`, `internal/auth`, `internal/update`, `docs/failure-modes.md` |
| D. Docs and contributing | `v030/docs` | `README.md`, `docs/` except the two files above, `CONTRIBUTING.md`, `.github/` templates |
| E. Identity, roles and access per route | `v030/identity` | `internal/auth` (OIDC, JWKS cache, roles), access rules on routes, the identity on each request |
| F. Admin API and audit log | `v030/admin` | `api/openapi.yaml`, `internal/admin`, the audit log and its store tables |
| G. Postgres and several replicas | `v030/postgres` | `internal/store/postgres`, the shared counter store for limits, migrations that run on both stores |
| H. Metrics, tracing and demo | `v030/observability` | `/metrics`, OTLP tracing, the `<project>_*` metric names, a `demo/` Docker Compose that runs in five minutes |
| I. OpenAI Responses API | `v030/responses` | `POST /v1/responses` (#42) |
| J. Images in chat | `v030/vision` | content parts in the canonical schema, image parts in every dialect (#41) |

Order between workstreams: E lands the identity type and role check first, as a small pull request, because F builds its permissions on it. F starts with the OpenAPI file and the audit store and wires roles in once E's first pull request is merged. G and C both touch `internal/store`: G adds the Postgres store behind the existing interfaces, C fixes SQLite, and both keep the shared store tests passing on both. H instruments the code the others change, so it merges last among the feature streams. J changes `schema.Message`, which B, I and every adapter read, so J lands its schema change as one early pull request and the others rebase on it. I starts after that.

The sessions start in rounds, features first, so the hardening work runs on the final code:

1. E, G and J: identity, Postgres with reload, and images.
2. F, H and I: the admin API, metrics with the demo, and the Responses API.
3. A: the load harness, the v0.2.4 baseline, profiling and bottleneck fixes.
4. B, C and D: the two bug hunts on the optimized code, using A's harness for load, and the docs.
5. The benchmark is run once more for the final numbers, then one pull request takes `next/v0.3.0` to `main`.

A change outside a workstream's area is fine when a fix needs it, but keep it small and say so in the pull request, since another session may be editing the same file. Merge `next/v0.3.0` into your branch before each pull request.

## Definition of done for v0.3.0

- [ ] Every bug found has a test that fails without the fix. No open issue labelled `bug`.
- [ ] `go test -race ./...` passes, and every fuzz target has run for at least 10 minutes without a crash.
- [ ] `docs/failure-modes.md` lists what can go wrong (upstream down, slow, partial stream, huge body, caller gone, store locked or full, clock jump, bad config, many replicas) and how transponder behaves, each with a test.
- [ ] `bench/` reproduces the numbers: the same load against v0.2.4 and against v0.3.0 on the same machine, with the method written down.
- [ ] `docs/benchmarks.md` has the before and after table: requests per second, p50/p95/p99 added latency, memory per request and allocations on the hot paths. No benchmark is more than 5% slower than v0.2.4, and each bottleneck the profiles found is fixed or explained.
- [ ] README rewritten for a newcomer and laid out with care (badges, demo screenshot, architecture diagram, feature and provider tables, comparison, collapsible reference): what it is, a 60-second start, every provider in one table, config reference, how it compares, how to help.
- [ ] CONTRIBUTING.md and the pull request template accept a pull request without an issue: small fixes and providers go straight to a pull request, larger changes start with a short design comment.
- [ ] Coverage at 80% or more, every required check green on `next/v0.3.0`.
- [ ] A caller signs in with an OIDC token from any standard provider, gets `admin`, `member` or `viewer`, and can only call the routes their rules allow. API keys keep working.
- [ ] `/admin/v1` covers what the console will need (status, keys, providers, routes, budgets, usage, audit) as described in `api/openapi.yaml`, with the list, error, version and `managed_by_file` rules from CONTRACT.md, and every write adds an audit record.
- [ ] With `store.postgres` set, two or more replicas share keys, config, usage and limits, and a budget holds across them. The same store test suite passes on SQLite and Postgres.
- [ ] `/metrics` serves the shared metric names, traces go out over OTLP when configured, and `demo/` brings up transponder with a fake upstream and a dashboard in five minutes.
- [ ] Keys, providers, routes and budgets can be created and changed through the admin API, with provider secrets encrypted at rest under `secrets_key`. A change reaches every replica within 2 seconds without a restart, and a config that fails to load leaves the old one serving.
- [ ] `POST /v1/responses` works for OpenAI-dialect targets, streamed and not, with usage, limits and fallback like chat.
- [ ] A chat request with images works across OpenAI, Anthropic and Gemini targets, and a target that cannot take images is skipped.
- [ ] CHANGELOG lists each change under Unreleased, so the release notes write themselves.

### A. Benchmarks and bottlenecks (`v030/bench`)

- [ ] A fake upstream that answers chat (plain and streamed) and embeddings with a fixed latency and body size, and a load tool that drives transponder at a fixed rate and reports throughput, added latency percentiles, errors and memory. No network outside the machine.
- [ ] Run it against the v0.2.4 tag and record the baseline before anything changes.
- [ ] Go benchmarks for the hot paths: decoding and encoding chat requests, translating between dialects, router resolve and plan, the SSE relay, token counting, limits reserve and settle, usage recording.
- [ ] Profile CPU, memory and blocking under load. Fix the top bottlenecks, one pull request each, with the benchmark before and after in the description.
- [ ] `docs/benchmarks.md`: machine, method, how to run it, the before and after table.

### B. Bugs on the request path (`v030/request-path`)

- [ ] Read the request path end to end and list suspect behaviour first, then prove each with a failing test.
- [ ] Look at: a caller that disconnects mid-stream (#25), a stream that stalls, an upstream that sends a malformed or oversized event, headers and trailers on errors, unicode and very large messages, tool calls across dialects, concurrent requests sharing state, context cancellation reaching the upstream.
- [ ] Add fuzz targets where input comes from outside: every decoder and the SSE reader.
- [ ] Run `go test -race` with high `-count` on these packages.

### C. Bugs on the control path and failure modes (`v030/control-path`)

- [ ] Same method as B for config loading and env overrides, the router and cooldown, limits and budgets under concurrency, the SQLite store (locked database, full disk, migrations on an old file), API keys, and the update check.
- [ ] `${VAR}` expansion edge cases left open on #127: a comment line indented less than a block scalar's content still counts as content; a quoted scalar that spans lines and has a line starting with `#` is no longer expanded; a block header with an anchor or tag (`key: &a |`, `key: !!str |`) is not recognised. Fix each with a failing test, or replace the line scanner with expansion on parsed YAML nodes.
- [ ] Write `docs/failure-modes.md`, one section per failure, each pointing to its test.

### D. Docs and contributing (`v030/docs`)

- [ ] Make the README look good and carry detail, not only text:

  - A Mermaid diagram of the request path (caller, auth, router, limits, provider adapters, fallback, store, metrics and traces).
  - A features section grouped by area (routing and fallback, providers, auth and roles, limits and budgets, admin API, observability, deployment), each item one line with a link to its doc.
  - A provider table with dialect, chat, streaming, tools, images, embeddings and Responses API support, checked against the registry by a test so it can't drift.
  - A comparison table against LiteLLM Proxy and other gateways on the points that matter (single binary, memory, added latency from `docs/benchmarks.md`, OIDC, admin API, Postgres replicas), stated fairly with sources.
  - Quick start three ways (binary, Docker, `demo/`), each copy-paste ready, and a short "what's new in v0.3.0" block with the before and after numbers from A.
  - Collapsible `<details>` sections for long reference parts so the page stays easy to scan, and a table of contents.
  - Check it renders well on GitHub in light and dark mode, and that every link and anchor resolves.
- [ ] A configuration reference that lists every key with its default, generated or checked by a test so it can't drift.
- [ ] CONTRIBUTING.md and `.github/PULL_REQUEST_TEMPLATE.md`: pull requests without an issue are welcome. Make the same change in `contributing/` in raven-clown/mothership.
- [ ] `docs/architecture.md`, linked from the README and from `docs/design.md`: how the code is built and why, for a contributor reading it for the first time.
  - Mermaid diagrams: the package map (`server`, `auth`, `router`, `limits`, `provider`, `dialect`, `schema`, `store`, `runtime`, `admin`, `telemetry`) and the life of one chat request through the middleware, router, fallback and stream relay.
  - The design choices, each with the file that shows it and why it was chosen: small interfaces instead of class hierarchies (`provider.Provider`, the split `store` interfaces such as `KeyStore` and `KeyAdminStore`); the adapter pattern where OpenAI-compatible providers are presets over one adapter (`openai.Options`); the provider registry as a factory; the canonical schema as a hub so each dialect needs one translator pair instead of one per pair of dialects; middleware as decorators around `http.Handler`; copy-on-write config reload through `atomic.Pointer[Snapshot[T]]` so reads take no lock and in-flight requests keep their config; the stream encoders as small state machines; typed `provider.Error` driving fallback.
  - What the project avoids on purpose (deep inheritance, DI frameworks, ORMs) and the Go idioms used instead.
  - How it is tested: the shared store contract suite run on SQLite and Postgres, `httptest` fake upstreams, fuzz targets and race runs, with pointers to each.
  - A short "add a provider" and "add a dialect" walkthrough that follows the patterns above.
- [ ] Leave the benchmark numbers and the failure-mode list to A and C; link to their docs.

### E. Identity, roles and access per route (`v030/identity`)

- [ ] OIDC: validate JWTs against a configured issuer with a cached JWKS (refresh on unknown `kid`, bounded), audience check, clock skew allowance. Map claims to user, teams and role. API keys keep working and carry a role too.
- [ ] Roles `admin`, `member`, `viewer` as in CONTRACT.md, and access per route: a route can list the users, teams or roles allowed to call it; a denied call is 403 with the route named.
- [ ] Tests with a local JWKS server and signed tokens: valid, expired, wrong audience, unknown key, rotated key, missing claims. No outside network.

### F. Admin API and audit log (`v030/admin`)

- [ ] `api/openapi.yaml` first, reviewed against CONTRACT.md's admin rules: `GET /admin/v1/status`, keys, providers, routes, budgets and profiles, usage, and `GET /admin/v1/audit`. Items from the YAML file are read-only and marked `managed_by_file`.
- [ ] Handlers in `internal/admin` checked against the OpenAPI file by a test, cursor pagination, `If-Match` versions with 409 `version_conflict`, errors that name the field.
- [ ] An audit record for every write, with who, what, when and the request id, stored in the same store.
- [ ] Writes for keys, providers, routes, budgets and profiles, so a new user never has to write YAML. Provider secrets are encrypted with `secrets_key` before they reach the store and never returned by the API.
- [ ] Every write bumps `config_version` in the same transaction. On one replica the handler reloads before it answers.

### G. Postgres and several replicas (`v030/postgres`)

- [ ] `store.postgres` with `pgx`, migrations that run on both stores (expand and contract), and the store test suite run against SQLite and Postgres (Postgres in CI as a service container).
- [ ] A shared counter store so limits and budgets hold across replicas, with the in-process one as the fallback when only one replica runs. Config changes reach every replica within 2 seconds.
- [ ] A test that runs two transponder processes against one Postgres and checks a budget is not overspent.
- [ ] Reload as in design section 9: each replica checks `config_version` every 2 seconds, loads and validates the whole runtime config, and swaps it in atomically. A config that fails to load keeps the old one serving and shows in `/admin/v1/status`. In-flight requests finish on the config they started with.

### H. Metrics, tracing and demo (`v030/observability`)

- [ ] `/metrics` with `transponder_requests_total`, `_request_duration_seconds`, `_inflight_requests`, `_limited_total`, `_events_dropped_total`, plus tokens and cost by provider and model. Labels stay bounded.
- [ ] OTLP tracing when configured: one span per call and per upstream attempt, `traceparent` kept and forwarded.
- [ ] `demo/`: Docker Compose with transponder, the fake upstream from `bench/`, Prometheus and a Grafana dashboard. From clone to a working dashboard in five minutes, written up in the README.

### I. OpenAI Responses API (`v030/responses`)

- [ ] `POST /v1/responses` as scoped in #42: passthrough to targets with the OpenAI dialect, only `model` rewritten, streamed or not. Usage read from `response.completed` or the final body, so headers, usage records, limits and fallback work as for chat. Targets without the OpenAI dialect are skipped.
- [ ] Decide in the pull request what happens to `store` and `previous_response_id` when fallback moves the next call to another provider, and document it.
- [ ] Tests against an `httptest` upstream replaying recorded Responses API bodies.

### J. Images in chat (`v030/vision`)

- [ ] `schema.Message` carries ordered content parts: text, and images as a URL or base64 data with a media type (#41). Land this change first, as its own pull request.
- [ ] OpenAI `image_url` parts (including `data:` URLs), Anthropic image blocks and Gemini inline data, in and out. A target that cannot take images is skipped, as fallback already does for content it cannot carry.
- [ ] A size cap for inline images, and a decision on counting image tokens before the provider reports usage.
