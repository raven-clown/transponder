# v0.3.0: hardening, speed and docs

> Steps use checkbox (`- [ ]`) syntax for tracking. Follow the rules in AGENTS.md.

**Goal:** v0.3.0 adds no big feature. It makes what v0.2.4 already does correct under stress, measurably faster, and easy to adopt. Every claim in the release notes is backed by a test or a measured number. Access per route, OIDC, the admin API and Postgres (roadmap item 7) move to v0.4.0.

**How the work is split:** four workstreams run in parallel, each in its own session and branch off `next/v0.3.0`. Each workstream opens pull requests into `next/v0.3.0`, not into `main`. When every workstream is done, one pull request takes `next/v0.3.0` into `main`, and v0.3.0 is released from it.

| Workstream | Branch | Owns |
|---|---|---|
| A. Benchmarks and bottlenecks | `v030/bench` | `bench/`, `*_bench_test.go`, `docs/benchmarks.md`, hot-path changes the profiles point at |
| B. Bugs on the request path | `v030/request-path` | `internal/server`, `internal/dialect`, `internal/sse`, `internal/provider`, `internal/tokens` |
| C. Bugs on the control path and failure modes | `v030/control-path` | `internal/config`, `internal/router`, `internal/limits`, `internal/store`, `internal/auth`, `internal/update`, `docs/failure-modes.md` |
| D. Docs and contributing | `v030/docs` | `README.md`, `docs/` except the two files above, `CONTRIBUTING.md`, `.github/` templates |

A change outside a workstream's area is fine when a fix needs it, but keep it small and say so in the pull request, since another session may be editing the same file. Merge `next/v0.3.0` into your branch before each pull request.

## Definition of done for v0.3.0

- [ ] Every bug found has a test that fails without the fix. No open issue labelled `bug`.
- [ ] `go test -race ./...` passes, and every fuzz target has run for at least 10 minutes without a crash.
- [ ] `docs/failure-modes.md` lists what can go wrong (upstream down, slow, partial stream, huge body, caller gone, store locked or full, clock jump, bad config, many replicas) and how transponder behaves, each with a test.
- [ ] `bench/` reproduces the numbers: the same load against v0.2.4 and against v0.3.0 on the same machine, with the method written down.
- [ ] `docs/benchmarks.md` has the before and after table: requests per second, p50/p95/p99 added latency, memory per request and allocations on the hot paths. No benchmark is more than 5% slower than v0.2.4, and each bottleneck the profiles found is fixed or explained.
- [ ] README rewritten for a newcomer: what it is, a 60-second start, every provider in one table, config reference, how it compares, how to help.
- [ ] CONTRIBUTING.md and the pull request template accept a pull request without an issue: small fixes and providers go straight to a pull request, larger changes start with a short design comment.
- [ ] Coverage at 80% or more, every required check green on `next/v0.3.0`.
- [ ] CHANGELOG lists each change under Unreleased, so the release notes write themselves.

---

### A. Benchmarks and bottlenecks (`v030/bench`)

- [ ] A fake upstream that answers chat (plain and streamed) and embeddings with a fixed latency and body size, and a load tool that drives transponder at a fixed rate and reports throughput, added latency percentiles, errors and memory. No network outside the machine.
- [ ] Run it against the v0.2.4 tag and record the baseline before anything changes.
- [ ] Go benchmarks for the hot paths: decoding and encoding chat requests, translating between dialects, router resolve and plan, the SSE relay, token counting, limits reserve and settle, usage recording.
- [ ] Profile CPU, memory and blocking under load. Fix the top bottlenecks, one pull request each, with the benchmark before and after in the description.
- [ ] `docs/benchmarks.md`: machine, method, how to run it, the before and after table.

### B. Bugs on the request path (`v030/request-path`)

- [ ] Read the request path end to end and list suspect behaviour first, then prove each with a failing test.
- [ ] Look at: a caller that disconnects mid-stream (#25), a stream that stalls, an upstream that sends a malformed or oversized event, headers and trailers on errors, unicode and very large messages, tool calls across dialects, concurrent requests sharing state, context cancellation reaching the upstream.
- [ ] Add fuzz targets where input comes from outside: every decoder and the SSE reader.
- [ ] Run `go test -race` with high `-count` on these packages.

### C. Bugs on the control path and failure modes (`v030/control-path`)

- [ ] Same method as B for config loading and env overrides, the router and cooldown, limits and budgets under concurrency, the SQLite store (locked database, full disk, migrations on an old file), API keys, and the update check.
- [ ] Write `docs/failure-modes.md`, one section per failure, each pointing to its test.

### D. Docs and contributing (`v030/docs`)

- [ ] Rewrite README.md as described in the definition of done. Every YAML example must load with `transponder --config-test`.
- [ ] A configuration reference that lists every key with its default, generated or checked by a test so it can't drift.
- [ ] CONTRIBUTING.md and `.github/PULL_REQUEST_TEMPLATE.md`: pull requests without an issue are welcome. Make the same change in `contributing/` in raven-clown/mothership.
- [ ] Leave the benchmark numbers and the failure-mode list to A and C; link to their docs.

### Release (the coordinating session)

- [ ] Merge each workstream's pull requests into `next/v0.3.0` once green.
- [ ] Rerun the benchmark against v0.2.4 and `next/v0.3.0`, fill in the final table.
- [ ] One pull request from `next/v0.3.0` to `main`, then a `chore(release): v0.3.0` pull request and the release.
